# Session Guard v1.2 — agreed design

State: design agreed with the user on 2026-10-31; implemented in 1.2.0 on 2026-11-01 (item 9: no quota in the cloud).
The user installs and tests the final v1.2 themself (PC); a partner tests the cloud install. Claude only builds and
runs test installs. Work on `main`. All user-facing messages are in the user's language.

## 1. Per-prompt line (done, 81b453f)
The `[Session Guard] Context: …` line goes out only together with an instruction; a plain prompt adds nothing.

## 2. Break threshold 125k → 100k
Everywhere (`BREAK_CONTEXT`, RULES text, README, tests). Reason: a 125k session re-read after a break is ~250k.

## 3. One-step install (local)
- README gives one line the user pastes to Claude (like the cloud one); Claude adds the marketplace and installs
  the plugin. Then the user fully quits and reopens Claude **once**. No second restart.
- Setup starts by itself: in the first session after the restart, the hook tells Claude to run the setup skill at
  once and ask the single approval question (no `/session-guard:setup` to type; the command stays for manual use).
- Setup takes effect at once (activation is read on every hook call; settings are reloaded by the watcher).
  Sessions that started while setup was pending got no rules at start: their next prompt gets RULES once (state flag).
- The approval covers the conflict removals and the statusLine change (item 7). Declined → Session Guard stays off.
- Last setup message: fully quit Claude (tray included) and reopen it; until then other open sessions are unprotected.

## 4. Restart lock (sessions started before the install)
- Fact (docs): plugins load at session start or with `/reload-plugins`; a session process started before the
  install runs no Session Guard code, so it cannot be locked. Restarting the app reloads every session (`--resume`).
- A session whose prompt hook runs but whose SessionStart (since this install) never ran — the installing session,
  or one after `/reload-plugins` — gets the `restart` lock: every prompt is blocked with "This session started before
  Session Guard. Your message was not sent. Fully quit and reopen Claude, then continue here."
- SessionStart writes a per-session marker; the lock clears when the marker exists after the install time.
- Cloud: the installing session gets the repo hooks mid-session (settings watcher) → same lock, message says
  "open a new session" (item 10).

## 5. Lock types
`context` (hard limit), `finish`, `break`, `restart`, `quota`, stored separately (e.g. `state["locks"][type]`;
migrate v1.1 `locked`). Only `restart` (marker) and `quota` (reset passed / lower reading) clear by themselves;
clearing one never clears another.

## 6. Session Follow (quota)
- Files, one per window, shared by all local sessions (the quota is per account):
  `~/.claude/session_guard/session_follow/five_hour.json` and `weekly.json`
  = `{used_percent, resets_at (epoch), read_at, source}`. Files are never deleted: after `resets_at` the content is
  cleared and new data written over it. Weekly = the "all models" window.
- Sources (measured 2026-10-31):
  - Terminal CLI: statusLine JSON `rate_limits.five_hour / seven_day` (`used_percentage`, `resets_at`), zero tokens
    (docs: code.claude.com/docs/en/statusline; Pro/Max/Ultra, after the first API response).
  - Desktop app: statusLine does NOT run (tested). Claude calls `mcp__ccd_session_mgmt__get_usage`; a PostToolUse
    hook parses `plan.windows[]` (`label` "5-hour limit" / "Weekly · all models", `percentUsed`, `resetsAt`).
    ~400 tokens per reading (estimate), done in parallel with Claude's next tool call.
  - Cloud: item 9.
- Cadence: a reading older than 20 min → the hook asks for one (prompt or during work). 5-hour ≥85% or weekly ≥95%
  → every prompt (during long work: design choice, at most every 5 min). Estimate: ~15 readings per 5 h ≈ 6k tokens.
- Trigger: 5-hour ≥90% or weekly ≥98%, and the reset is ≥45 min away:
  - QUOTA STOP instruction: no new task; bring the current work to a hand-over-ready state within 15 min; write
    only one line to STATUS.md ("stopped at: which operation, in which state"), no hand-off note; then `quota` lock.
  - After 15 min the turn is stopped (`continue: false`) and locked.
  - Reset < 45 min away → no lock, work continues.
- While locked: every prompt is blocked: "Quota X% (5-hour/weekly), resets at HH:MM. Continue after that."
- New sessions and new projects while a shared reading is above the threshold and its reset is ahead: locked at
  once, no review, no file creation. The value cannot drop before the reset, so no new reading is needed.
- After the reset: the lock clears. Long mode or gap ≤ 1 h → continue. Normal mode and gap > 1 h → break rule
  (100k): the first prompt goes into the hand-off note, the hand-off is reported ready, the session locks.
- If a lock cannot be held (cloud, item 9): an important warning asks the user's permission to continue.

## 7. statusLine (terminal)
- Setup writes a signed statusLine command into `~/.claude/settings.json` (after approval; declined → not installed).
  The approval text says what is written and why, and that the code is public on GitHub under the MIT license.
- Existing statusLine: signed (an older Session Guard one) -> replaced. Unsigned (another tool) -> left alone,
  no terminal quota readings (user decision 2026-11-01: no wrapping; the code is open, anyone can adapt it).
- No unsigned Session Guard statusLine exists on the user's PC (checked 2026-10-31).

## 8. Project review before creating files (every new project)
Before CLAUDE.md, docs/STATUS.md, docs/STATUS_ARCHIVE.md are created, scan for files doing the same job under any
name: AGENTS.md, GEMINI.md, .cursorrules, .cursor/rules, .windsurfrules, .clinerules,
.github/copilot-instructions.md, HANDOFF*, NOTES*, TODO*, PROGRESS*, CONTEXT.md, MEMORY.md, any *status* file.
One list, one approval: conflicting lines deleted, useful content moved into STATUS/ARCHIVE, existing files edited,
missing ones created. Declined → Session Guard stays off.

## 9. Cloud quota — not possible: Session Follow is not offered in the cloud
- No hook can see the near-limit warning (docs, hooks page read in full: no hook input carries rate-limit data;
  Notification `quota_auto_resume_*` and StopFailure `rate_limit` fire only after the limit is hit). The app shows
  the warning as its own notification; it does not reach Claude or the hooks.
- `/usage` in headless/stream-json mode (CLI 2.1.316, cloud) emits no `usage_report` / rate-limit data
  (test branch claude/sleepy-ritchie-jb7oca); the SDK `usage_report` is only for SDK hosts (the apps).
- No unofficial route (account/plugin ban risk). README says plainly: no quota protection in cloud sessions.
  Cloud keeps every other rule (thresholds, break, locks, 24 h watch).
- The phone's /usage screen shows the numbers, but the app draws it; the session record gets only
  "You are currently using your subscription…" (checked), so a hook cannot read it.

### Test record
- Tests (test repo ocpipun/session-guard-cloud-test, 2026-10-31): statusLine does not run; no file, log or
  `~/.claude.json` key holds the numbers; no usage tool in the session; `/usage` prints only "You are currently
  using your subscription…" (phone) or opens the settings menu (desktop UI). Local commands' output does reach the
  transcript (`type: system, subtype: local_command`), but /usage carries no numbers.
- Unofficial routes (OAuth usage endpoint with the account token) are not used.
- Rejected: the user typing numbers or attaching screenshots (tiring; copying is not possible on the phone).

## 10. Cloud install (CLOUD.md)
One command per repository. The installing session: copies the files, writes the hand-off note into
docs/STATUS.md (creates it if missing, else overwrites the hand-off section), commits to the default branch, then
says: open a new session; older sessions of this repo stay unprotected. The scan, CLAUDE.md and STATUS work happen
at the start of the new session (review runs by itself, item 3).

## 12. Install flow as built (user decision 2026-11-01, replaces 3, 4 and 10 where they differ)
- Computer: one pasted line -> INSTALL.md: install, scan, one list (+ language question if the app language
  cannot be read), one approval, all in the installing session. After approval, sessions that started before the
  install are locked (restart lock only once setup is active, so setup answers get through). Last step: fully quit
  and reopen; afterwards nothing is typed or asked.
- Cloud: CLOUD.md: review list + "Which language would you like session-guard notices in?" + one approval before
  anything is copied; then install (--reviewed), language, hand-over-ready work, hand-off note, commit to the
  default branch; the session locks. Last step: open a new session, which asks nothing.
- Notice language: chosen once at setup (desktop app config.json "locale", read once), never checked again;
  another language only on the user's request. Terminal English.

## 11. Before the user's install
Remove Session Guard v1.0 from the PC as the last step of a session, then the user restarts the app: plugin entry,
marketplace entry, `~/.claude/plugins/{cache,marketplaces,data}/session-guard*`, `~/.claude/session_guard`.
Not while sessions run: the hook would call a missing script, Python exits 2, and exit 2 blocks every prompt.
The user's own CLAUDE.md lines and `~/.claude/scripts/oturum_olcum.py` stay for setup to handle.
